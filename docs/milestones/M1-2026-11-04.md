# M1 — Static bootstrap and archive-access investigation

Date: **4 November 2026**. Task-checklist scope remains `m0-2026-11-04`; no denominator or task-completion change is made by this checkpoint.

The private Windows lab now has reproducible Ghidra analysis of the startup components, a corrected archive classification and a wider independently checked candidate search. **No current-build archive key, complete native game implementation or playable build was recovered.**

## Evidence

| Receipt | Observed result | Limit |
| --- | --- | --- |
| `m1-archive-classification` | All 75 files with the `.pak` extension were classified: 17 have standard Unreal v12 footers and 58 are validated Chromium DataPack v5 resources. Of the Unreal PAKs, 16 have encrypted indices and one is clear. | Filename extensions alone are not container-format evidence. The 58 Chromium files are 55 locale packs and three browser-resource packs. |
| `m1-candidate-audit` | 54 unique supplied candidates were checked against two distinct encrypted PAK indices with both the private full-index-checksum tool and CUE4Parse: 108 candidate/index pairs per validator, with zero matches. | This was a bounded candidate audit, not exhaustive AES-256 search. Values and inputs remain private. |
| `m1-schedule-audit` | A separate detector inspected 379,715,584 initialized/readable PE-section bytes across 47 files for consistent forward AES-256 expanded-key schedules, in both word byte orders. No schedule candidates were found. Published positive controls and a corrupted negative control passed. | This does not exclude raw, scattered, transformed or runtime-generated keys. It is not evidence that the game has no key. |
| `m1-clear-index` | The clear CrashReportClient PAK mounted normally under `Engine/`, exposing 6,943 entries with zero encrypted entries. Its plaintext index checksum matched its footer. | Only an index manifest was recorded. This is engine/crash-reporter content, not recovered WARDOGS gameplay assets. |
| `m1-coreinit-loader` | Bounded Ghidra work produced 22 private decompiler outputs for the small loader and instruction evidence for selected routines. A visible path maps and relocates the sibling runtime and delegates initialization with 38 observed context-field assignments. A bounded raw-instruction continuation followed the saved context argument and simplified selected indirect frame accesses. | The context layout is assignment-derived. No downstream context-object dereference or archive-key derivation has been established. This does not demonstrate decoding the main executable. Decompiler output is not original source. |
| `m1-launcher-boundary` | Twelve selected launcher functions were decompiled. The visible path prepares a session through a local service and passes a session result to the launched process. | No session was created or contacted. A bootstrap session value is not an established archive key. |
| `m1-runtime-crypto` | Two bounded runtime routines contain 123 instruction-confirmed AES operations. Their visible interfaces take a 32-byte key through an argument and process caller-supplied data. | No literal key was identified inside those routines. Their relation to PAK encryption, protected code or other data is not established. A caller-byte candidate does not yet prove its incoming key argument. |
| `m1-memory-correlation` | Seven selected runtime regions were compared between the copied file and Ghidra memory; all seven matched byte for byte. A raw-instruction trace explained the entry wrapper hidden by the decompiler's simplified presentation. | A local overlap warning is not proof that the entire startup path is unrecoverable. Further indirect control flow and key provenance remain unresolved. |
| `m1-state-processor` | The extended trace reached the state processor's real terminal. A separate focal Ghidra job decompiled its 53,849-byte range, with every byte matching the copied file. Version-aware Boolean identities proved selected constants and a saved-frame index. | The terminal indirect destination remains unresolved. Unknown state inputs and decompiler jump warnings are retained; no original gameplay or archive key was recovered. |
| `m1-restored-layout` | The protected image and pinned public restored-image metadata match in PE timestamp, image base, entry RVA, image size and all ten section RVAs/virtual sizes. Their total file-size difference exactly matches the documented relocation-section expansion. | This strongly supports a common layout, not equal decoded bytes or verified crypto-symbol semantics. The raw restored/decompiler corpus is absent from the public checkout. |
| `m1-passive-bootstrap` | The bundled MSI and its service/control programs were extracted as data. The MSI hash matched its manifest. Static service analysis exposes session RPC references and modular interfaces; two focused RPC regions match Ghidra memory byte for byte. | No component was installed or executed. Selected decompilation failures are explicit; handlers must not be called absent. A session/module framework is not an established archive-key provider. |

The original game, loader, runtime and launcher were not executed or patched. No game process was injected, no service or driver was installed or changed, and no game/backend request was sent. Private reports, addresses, pseudocode, candidates and game content remain outside this repository.

The two passively extracted bootstrap programs were also checked separately for the supported literal-key representations and forward AES-256 schedules. They produced no additional candidates. The original 54-candidate pool and its validation counts are unchanged; these negative scans do not establish absence of other key forms.

## Correction to M0 inventory wording

M0 described **75 PAK containers** based on filename extension. The verified classification is **75 `.pak` filenames: 17 standard Unreal PAKs plus 58 Chromium DataPacks**. The current metadata and the M0 note now make that distinction explicit. The separate count of **17 IoStore TOCs, 15 marked encrypted**, is unchanged. IoStore chunk entries are not asset counts.

## What this changes

The investigation can now distinguish the archive cipher, the protected executable image, the small loader's mapping work and the launcher's service/session boundary. Finding AES instructions or a session identifier is insufficient to identify the archive key; every candidate still needs independent validation against the actual encrypted indices.

The remaining key-provenance work follows readable caller arguments and the partially traced initialization context. Current-build property mappings, reconstructed editor assets, native gameplay, engine compilation, independent multiplayer and physical iPhone validation are still pending.

The per-sector bars remain **lab/toolchain 6/8 (75%)**, **data recovery 1/6 (16.7%, inventory only)**, and **zero completed tasks in every game/runtime sector**. These research results do not complete the existing implementation tasks. Overall game completion remains unknown.
